## Opinión UX/producto — pantalla `/mi/rutina`

Lo que funciona bien:
- El copy explica el motivo de cada decisión técnica en comentarios (RLS,
  padding-bottom por el timer fijo) — buena señal de que la UI ya fue
  iterada con casos reales, no a ciegas.
- Estado "cuota vencida" bloquea con CTA claro a pago y no deja ver la
  rutina — correcto para el negocio, evita fricción de soporte.
- Acordeones (`entradaManual`, `regenerarDetails`, `MasOpcionesAcordeon`)
  mantienen el flujo principal (ver/entrenar) arriba y esconden lo
  secundario (regenerar, armar a mano, PDF, calendario) — jerarquía correcta
  para un alumno que abre esto en el vestuario, apurado.

Fricciones que valen la pena mirar:
- **Waterfall de queries en el server component** (`page.tsx:55-114`):
  `cliente` → `aforo`/`gymData` → `rutina` → `items`. `aforo` y `gymData`
  solo dependen de `cliente.gimnasio_id`, podrían dispararse en paralelo con
  `Promise.all` en vez de secuencial. En mobile con LTE esto es la
  diferencia entre "instantáneo" y "se nota el salto". No lo toqué porque
  cambia el orden de ejecución del componente — lo dejo para que decidas si
  vale la pena vs. el riesgo de tocar un server component grande.
- **Rutina Express de retención** (`aceptarRutinaExpressRetencion`) genera
  una rutina genérica fija (`tonificar`, `principiante`, 2 días, sin
  enfasis) sin pedirle nada al usuario. Es una decisión de producto
  deliberada (retención rápida), pero vale confirmar que el usuario no
  espera que respete sus preferencias previas — si tenía una rutina de
  "hipertrofia avanzado 4 días", el reemplazo por una genérica de 2 días
  puede leerse como un downgrade no pedido.

## Sweep auth + cuotas (2026-09-14)

### P1 — validación de firma débil, no explota por diseño pero es defensa rota [RESUELTO]
- `src/app/api/webhooks/mercadopago/route.ts:45-51` — si el atacante omite el header `x-signature`, la validación de firma se saltea entera (`if (xSignature)`); y si lo manda, solo se rechaza cuando `NODE_ENV === "production"` (en preview/staging una firma inválida pasa igual). No es explotable para forjar pagos porque el estado real se re-consulta a la API de MP con el token del gimnasio (mismo patrón que `mercadopago.ts:81-83`, documentado como intencional), pero deja sin defensa en profundidad al entorno de preview y complica auditar quién llamó al webhook.

### Limpio (falsos positivos descartados)
- `panel/clientes`, `panel/caja`, `panel/plan`, `panel/ajustes`, `panel/planes`: el sweep inicial marcó 0 guards por buscar solo `requireProfile/requireRole`; todos usan `requireDueno`/`requireStaffODueno` correctamente (guard real, no vulnerabilidad).
- `admin/actions.ts`, `admin/partner/actions.ts`: usan `requireSuperadmin()` en cada export, service_role justificado.
- Rutas con 0 guards y sin sospecha: `login`, `registro-*`, `cambiar-clave` (valida `auth.getUser()` propio), `inicio` (landing pública con honeypot), `r/[slug]` (plantilla pública), `aforo` (solo lectura, RLS).
- `/api/cron/cuotas`: protegido con `CRON_SECRET` vía header `authorization`. `recalcular_estado_cuota()` corre ahí, sin exposición pública.
- `/api/pagos/webhook` y `/api/pagos-socio/webhook`: no dependen del body del atacante — reconsultan el pago real a la API de MP (con el token del gimnasio/plataforma) antes de aprobar nada. Diseño correcto.
